0. 章节导言

为什么先学定位？因为 mem0 所有的设计决策（ADD-only、实体链接、多信号融合）都从它想当什么、不想当什么出发。先建立"它在生态里的位置"，后面的每个实现细节就有了锚点——你会反复用一句话校准理解：mem0 回答"哪些持久事实对当前用户最相关"，向量库回答"哪段文本最像"。

这一章解决三件事：mem0 是什么（kp01-01）、它与最容易混淆的三个方案差在哪（kp01-02）、什么时候该选它而非 Zep/Letta/LangMem（kp01-03）。

1. mem0 是什么与生态位（kp01-01）

1.1 学习目标

学完你能回答：mem0 解决什么问题、用什么核心机制解决、它明确拒绝做什么。

1.2 讲解 + 源码走读

痛点：LLM 本身无状态。跨会话的个性化——记住用户偏好、上次的决定、长期的约束——需要把对话变成可检索的持久记忆。

核心机制（一句话）：白盒记忆——写路径用 LLM 把对话蒸馏成自包含事实（而非存原始对话块），读路径做语义 + 关键词 + 实体多信号融合召回，并按 user_id / agent_id / run_id 隔离。

生态位（它站在哪）：一条光谱上——

裸向量库 ───────────── mem0 ──────────── 完整 Agent 框架
只做文本相似           事实抽取+召回        Letta/LangMem
无写路径逻辑            +生命周期            Agent 自治记忆

mem0 不是向量库（那是"怎么存"的实现），也不是 Agent 框架（那是"怎么用记忆思考"）。它占据事实记忆层——最容易被误读成"RAG"或"向量库封装"，但它的设计核心在存什么（LLM 抽取）和怎么取（多信号融合 + 隔离 + 生命周期）。

证据：mem0/configs/prompts.py:468 的 ADDITIVE_EXTRACTION_PROMPT 强制 LLM 输出 {"memory":[{id,text,attributed_to,linked_memory_ids}]}——这就是"把对话变成事实"的契约；mem0/memory/main.py:906-1196 的 V3 管线把一次对话蒸馏成若干持久事实。

1.3 小结

  • mem0 解决 LLM 无状态 → 跨会话个性化需要持久可检索记忆。
  • 核心是白盒记忆：写路径蒸馏事实，读路径多信号召回，非存原始对话块。
  • 生态位：事实记忆层，介于裸向量库与完整 Agent 框架之间。
  • 误区红线：它的问题不是"记忆存哪里"（向量库只是实现），而是"存什么 + 怎么取"。

1.4 课后思考题

  • kp01-01（design）：如果面试官说"mem0 不就是把记忆存到向量库吗"，你如何用一句话纠正，并指出它的设计核心实际在写路径的哪个决策上？

2. 与裸向量库/RAG/Claude Code auto memory 的本质差异（kp01-02）

2.1 学习目标

学完你能：面对"mem0 和 RAG 有什么区别""和 Claude Code 的记忆有什么区别"这类问题，给出本质维度的对比而非罗列功能。

2.2 讲解 + 源码走读

三个对比对象，三个本质维度：

维度裸向量库/自建 RAGClaude Code auto memorymem0
------------
写路径存原始 chunk，无抽取Claude 写自然语言 Markdown 笔记LLM 蒸馏成持久事实（main.py:930-959）
检索纯语义相似MEMORY.md 索引 + 模型上下文判断（无向量检索）语义 + BM25 + 实体融合（scoring.py:60-139）
作用域自己写按项目 git 根user/agent/run 内置（main.py:143）
生命周期自己写/memory 编辑 + Auto Dreamupdate/delete/history 完整 API

vs 裸向量库 / RAG：RAG 面向外部知识（文档 chunk），mem0 面向用户事实（抽取条目）。两者读路径都是"检索增强循环"，但 mem0 多了 RAG 没有的写路径——怎么提炼该记的东西，以及生命周期管理。裸向量库只回答"哪段文本最像"，mem0 回答"哪些事实对当前用户最相关"。

vs Claude Code auto memory：记忆形态决定架构。Claude Code 的记忆是稀疏、精确、人可读的"项目笔记"——量小、要求精确、上下文判断足够，引入向量语义召回反而有害（过拟合噪声）。mem0 是海量、模糊、机器检索的"事实库"——量大、召回需求模糊、必须打分排序。Pi 是 mem0 的用户（用 @mem0/pi-agent-plugin），不是对比项——Pi 是通用助手需要事实型记忆，所以直接集成 mem0。

2.3 小结

  • vs RAG：外部知识 vs 用户事实；读路径同，写路径 mem0 独有。
  • vs 裸向量库：存什么（抽取 vs chunk）+ 怎么取（多信号 vs 纯语义）+ 生命周期。
  • vs Claude Code：记忆形态决定架构——稀疏精确笔记 vs 海量模糊事实库。
  • 记忆形态 → 架构是这条知识的可迁移结论（选型时先问形态）。

2.4 课后思考题

  • kp01-02（design）：为什么 Claude Code 的 auto memory 不做向量检索而 mem0 做？如果把 mem0 的思路强套到 Claude Code 的记忆场景，会在哪里变糟？

3. 与 Zep/Letta/LangMem 的选型判据（kp01-03）

3.1 学习目标

学完你能给出可迁移的决策规则：什么条件下选 mem0，什么条件下选 Zep/Letta/LangMem——而不是背一个 feature 列表。

3.2 讲解 + 源码走读

生态事实（[web] 2026-08-12，详见 positioning.md）：

方案核心动作最强点代价
------------
mem0LLM 抽取持久事实生态最大（~51.8k stars）、上手最快、OSS 自托管自由时间推理弱（LongMemEval temporal 49%）；graph 付费墙
Zep时间知识图谱（bi-temporal）时效/矛盾消解最强（temporal 63.8%）重度托管服务（CE 2025 已弃）、贵
LettaAgent 自编辑分层记忆长时自治 Agent（LoCoMo 74.0%）是框架不是 drop-in API、重
LangMemLangGraph 原生 store零新依赖（在 LangChain 生态内）绑死 LangGraph、LoCoMo 最低 58.1%

可迁移决策规则（这是 kp01-03 的"能力"所在）：

  1. 要不要在写路径做 LLM 蒸馏？ 不要 → 裸向量库 + 自写 RAG 足够。
  2. 要蒸馏 + 标准事实场景 → mem0（最省事、生态最全）。
  3. 要蒸馏 + 时间/矛盾消解（"什么时候变的"）→ Zep。
  4. 要蒸馏 + Agent 自治长时运行 → Letta。
  5. 已扎根 LangGraph → LangMem。
  6. 数据不能出境 → mem0 OSS 自托管 + 本地 LLM（18 LLM / 25 向量库，factory.py）。

判据来源锚点：positioning.md 的"When to pick it"行（[web] + [src] 双证）。

3.3 小结

  • 选型核心判据：要不要在写路径做 LLM 蒸馏 + 场景是否要时间推理。
  • mem0 的差异化 = 事实抽取 + 最大生态 + OSS 自托管自由；代价 = 时间推理弱。
  • Zep 赢在时效、Letta 赢在自治、LangMem 赢在 LangGraph 零依赖——各自换走了"简单 drop-in"。

3.4 课后思考题

  • kp01-03（design）：你的产品要给客服助手做长期用户画像记忆，要求数据不出域、且要处理"用户改主意"（偏好变更）——按决策规则，mem0、Zep、自建 RAG 里选谁？理由逐条列出（引用矩阵行）。

章节总结

本章心智模型：mem0 是站在光谱中间的事实记忆层——写路径蒸馏、读路径多信号召回、内置隔离与生命周期。对比任何方案时先问两个维度：存什么（chunk vs 事实 vs 笔记）与怎么取（纯语义 vs 多信号 vs 索引+上下文）。选型时最核心判据是写路径要不要 LLM 蒸馏 + 场景要不要时间推理。

关键 file:line 索引：main.py:930-959（LLM 抽取）、scoring.py:60-139（融合）、main.py:143（作用域剥离）、factory.py:42（Provider 注册）。

与整体架构的钩子：本章"白盒记忆"的框架，正是 m04/m05 的 add/search 数据流要展开的两半；m06 的 ADD-only 哲学是"写路径只蒸馏不裁决"的展开。
