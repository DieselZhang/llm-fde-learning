## 1. 为什么 ADD-only（kp06-01）

### 1.1 学习目标

学完你能：解释 ADD-only 的动机（为什么写路径不裁决）、对比旧版设计的失败点。

### 1.2 讲解 + 源码走读

**核心主张**：写路径只做**单调累积**（ADD），把"哪些记忆有效、哪些过期、哪些矛盾"的裁决权全部留给读路径反复打分。

**为什么（旧版教训）**：旧版 `extract + reconcile` 让 LLM 在**信息不充分**的状态下做一次性合并/删除判断——它只看到本次对话 + 少量旧记忆，却要决定"这条旧记忆该不该删"。**错误在写入期被不可逆固化**：一旦 LLM 误删一条有用记忆，它永远找不回来。且每次 add 两次调用（extract + reconcile），贵。

**V3 的转变**：

```
旧版: 写路径 = LLM抽取 + LLM合并/删除裁决   （两次LLM调用，错误不可逆）
V3:   写路径 = LLM抽取(仅ADD)               （一次LLM调用，错误可逆）
      裁决 → 读路径反复打分（哪个进上下文由 query 决定）
```

**哲学**："**memory is retrieval, not storage**"——记忆的价值在检索时兑现，不在写入时拍板。`main.py:930-959` 的抽取 prompt 只输出要新增的事实，无 UPDATE/DELETE 决策。

**代码证据**：`add()` 里没有任何"根据旧记忆改写/删除"的调用；`update`/`delete` 是**按 ID 的手动操作**（`main.py:1805,1859`），不由 LLM 驱动。

### 1.3 小结

- ADD-only = 写路径只单调累积，裁决权移给读路径。
- 旧版痛点：写路径在信息不充分时做不可逆合并/删除，误删找不回 + 两次调用贵。
- 哲学："memory is retrieval, not storage"。

### 1.4 课后思考题

- **kp06-01（design）**：ADD-only 把"矛盾事实消解"从写路径挪走，换来的是哪个确定的收益？请用"不可逆性"解释。

## 2. ADD-only 的代价与边界（kp06-02）

### 2.1 学习目标

学完你能：诚实列出 ADD-only 的 4 个代价、说出哪些是 OSS 无法自行解决的。

### 2.2 讲解 + 源码走读

**代价清单**（设计诚实性——面试加分项）：

| 代价 | 表现 | 缓解手段 |
|---|---|---|
| **无内置冲突消解** | 矛盾事实并存（"喜欢 Rust"与"改喜欢 Go"都在库），OSS 无机制保证挑对 | 读路径靠分数排挤；平台有 temporal scoring + Dream 合并 |
| **无时间衰减** | `reference_date` 在 OSS `search()` 直接抛错（`main.py:1422`） | 平台有；OSS 需自建 |
| **库只增不减** | 累积 + over-fetch 候选膨胀，检索成本上升 | 定期人工合并；平台 Dream 自动化 |
| **召回过时版本风险** | "改主意"后旧事实仍可能被召回 | 分数排挤 + 时间衰减（平台） |

**关键认识**：这些不是 bug，是 ADD-only 的**固有代价**——换取"错误不在写路径固化"。诚实承认边界，比假装系统完美更有说服力（面试红线：不要伪装系统无缺）。

**代码证据**：`main.py:1411-1422` 明确 `reference_date (Any, optional): Platform-only temporal parameter. Not supported in OSS.` 并抛错。

### 2.3 小结

- 四个代价：无冲突消解、无时间衰减、库只增不减、召回过时版本。
- 代价换取的是"写路径不固化错误"这个核心收益。
- 有些代价 OSS 无法自行解决（时间衰减），是平台的差异化空间。

### 2.4 课后思考题

- **kp06-02（design）**：用户"改主意"后，旧记忆仍然可被召回。请设计一个不破坏 ADD-only 的缓解方案（提示：时间戳 + 读路径过滤 vs 写路径合并，选哪个？）。

## 3. 平台 vs OSS 的功能分界（kp06-03）

### 3.1 学习目标

学完你能：说清 OSS 与平台各提供什么、哪些能力是平台独有、为什么。

### 3.2 讲解 + 源码走读

**分界总览**：

| 能力 | OSS | Platform |
|---|---|---|
| 纯 ADD-only 管线 | ✅ | ✅ |
| `reference_date` / 时间衰减 | ❌（抛错 `main.py:1422`） | ✅（temporal scoring） |
| `latest_only` | ❌ | ✅ |
| Dream 记忆合并 | ❌ | ✅（pi-agent-plugin 配置 `minHours:24 / minSessions:5 / minMemories:20`） |
| 图 memory（多跳关系） | ❌（已移除 #6808） | ✅（付费） |
| 托管运维 | ❌ | ✅ |

**为什么这样分**：

1. **复杂度归属**：时间推理（bi-temporal）、图遍历、自动合并都是**高复杂度**能力——塞进 OSS 会大幅增加维护面与使用门槛。OSS 保持"轻 + 可自托管"，重能力进付费平台（商业逻辑 + 复杂度管理双重合理）。
2. **图 memory 移出 OSS 的教训**：图 DB 运维贵、OSS 用户用不上；轻量实体链接（m04）覆盖主要价值，图推理留给平台（`#6808` 提交）。
3. **生态策略**：OSS 是引流入口（上手快、可自托管），平台是变现与深度能力的所在地——两者是同一产品的两个出口。

### 3.3 小结

- 平台独有：时间衰减 / temporal scoring / `latest_only` / Dream 合并 / 图 memory。
- 分界逻辑：高复杂度能力进平台，OSS 保持轻量可自托管。
- 图 memory 已从 OSS 移除（#6808）——讲 OSS 架构时别提 Neo4j。

### 3.4 课后思考题

- **kp06-03（design）**：如果你维护一个 OSS 项目，什么条件下会把一个能力从 OSS 移进付费版？（提示：维护成本 + 用户覆盖面 + 商业合理性）

## 4. 隐私/成本/合规边界（kp06-04）

### 4.1 学习目标

学完你能：说出 mem0 的隐私模型、成本结构、以及选型时的合规考量。

### 4.2 讲解 + 源码走读

**隐私**：

- **数据要发给 LLM**：抽取（`main.py:946-959`）与召回打分都依赖 LLM/embedding，文本会发送给 provider。
- **缓解**：OSS 自托管 + 本地 LLM（Ollama 等，18 个 provider）→ 数据不出域（`factory.py`）；这是 OSS 相对平台的核心卖点。
- **写路径 PII 脱敏**：平台有脱敏机制，OSS 需自建。

**成本**：

- **写路径是主要 LLM 成本**：每次 add 一次抽取调用；`infer=False` 可完全跳过 LLM（直接存原文，牺牲抽取）。
- **读路径是延迟敏感点**：over-fetch（`main.py:1631`）+ 融合计算，`top_k` 与阈值决定裁剪；读频率远高于写，延迟更敏感。
- **向量库/存储成本**：库只增不减（ADD-only 代价），需定期合并控制规模。

**合规决策链**：

1. 数据能否出境？否 → OSS + 本地 LLM。
2. 存储是否需自持？是 → OSS 自托管向量库（25 个选择）。
3. 成本敏感？→ 控写频率 / `infer=False` / 本地模型。

### 4.3 小结

- 隐私：数据发 LLM 是常态；OSS + 本地 LLM = 数据不出域。
- 成本：写路径烧 LLM token，读路径重延迟；`infer=False` 是跳过 LLM 的开关。
- 合规决策链：数据出境？→ 存储自持？→ 成本敏感？层层收窄。

### 4.4 课后思考题

- **kp06-04（design）**：一个金融客服产品要长期记忆用户偏好，但合规要求数据不出内网。请用平台/OSS 分界 + 成本结构，给出完整架构选择与理由。

## 章节总结

**本章心智模型**：mem0 的全部设计都围绕一个核心取舍——**写路径简单确定、读路径裁决**（ADD-only）。这带来四个固有代价（冲突/时间/膨胀/过时），平台用 temporal scoring + Dream 补齐，OSS 靠"诚实承认 + 轻量自托管"立足。选型时先回答三个问题：要不要写路径蒸馏？数据出不出域？要不要时间推理？——答案指向 mem0 / Zep / 自建 RAG。

**关键 file:line 索引**：`main.py:906-1196`（ADD-only 管线）、`:1411-1422`（reference_date 拒绝）、`:1805,1859`（手动 update/delete）、`prompts.py:468`（抽取只 ADD）、`factory.py`（本地 LLM 能力）。

**与整体架构的钩子**：这一章把 m04（写路径）和 m05（读路径）串成一条哲学主线——"写单调累积、读反复裁决"；m07 的"自研 vs 集成"决策链直接建在这章的成本/合规分析上。
