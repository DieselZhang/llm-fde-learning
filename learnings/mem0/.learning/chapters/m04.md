## 0. 章节导言

这是 repo-mastery 的核心价值模块——**关键实现**。m01-03 建立的是"地图"，这一章走进**写路径**：一段对话进来，如何变成几条可检索的持久事实。四个知识点层层递进：8 阶段总览（kp04-01）→ 抽取 + 防幻觉（kp04-02）→ 去重设计（kp04-03）→ 实体链接设计（kp04-04）。

**全景图**：

```
对话 → ①作用域校验 → ②取上下文(最近10条) → ③检索已有记忆(top-10, UUID→"0".."9")
    → ④单次LLM抽取(ADD-only, JSON) → ⑤批量embedding → ⑥MD5去重
    → ⑦批量写向量库 + SQLite记ADD → ⑧实体链接 → 保存消息 + 遥测
```

## 1. V3 add() 八阶段数据流总览（kp04-01）

### 1.1 学习目标

学完你能：按顺序说出 add() 的 8 个阶段、每阶段的输入输出、哪阶段是唯一的 LLM 调用。

### 1.2 讲解 + 源码走读

**8 阶段**（`main.py:906-1196`）：

| # | 阶段 | 做什么 | 证据 |
|---|---|---|---|
| 0 | 作用域校验 | 剥离身份键防篡改；要求 user/agent/run 至少一个 | `main.py:807-857`, `:143` |
| 1 | 取上下文 | 该会话最近 10 条消息（`get_last_messages`） | `main.py:908-911` |
| 2 | 检索已有记忆 | top-10，真实 UUID 重映射成 `"0".."9"` | `main.py:913-928` |
| 3 | **单次 LLM 抽取** | `ADDITIVE_EXTRACTION_PROMPT` 强制 JSON 输出 | `main.py:930-959` |
| 4 | 批量 embedding | 抽取文本 → 向量 | `main.py:981-993` |
| 5 | MD5 精确去重 | 对照已存 hash + 批内 set | `main.py:995-1033` |
| 6 | 批量写向量库 | 主集合 + SQLite 记 `ADD` 事件 | `main.py:1035-1074` |
| 7 | 实体链接 | spaCy 抽实体 → `_entities` 集合匹配 | `main.py:1077-1180` |
| 8 | 保存消息 + 遥测 | 滚动存 10 条；`capture_event` | `main.py:1182-1196` |

**关键设计**：**整个 add 只有一次 LLM 调用（阶段 3）**——无 UPDATE/DELETE 决策。这是 ADD-only 哲学的落地点：写路径单调累积，裁决权全部留给读路径（m06 深挖）。对比旧版（extract + reconcile）每次 add 两次调用且写路径做合并判断，V3 是一次调用 + 纯累积。

### 1.3 小结

- add() 8 阶段：作用域 → 上下文 → 已有记忆 → **单次抽取** → embed → 去重 → 写入 → 实体链接。
- 唯一 LLM 调用在阶段 3，且只做 ADD，不做 UPDATE/DELETE。
- 阶段 2 的 UUID 重映射为阶段 3 防幻觉服务（下节详述）。

### 1.4 课后思考题

- **kp04-01（concept）**：V3 相对旧版"extract + reconcile"，把哪个决策从写路径挪走了？挪走后的写路径剩下什么职责？

## 2. 单次 LLM 抽取 + UUID 重映射防幻觉（kp04-02）

### 2.1 学习目标

学完你能：解释抽取 prompt 的契约（输出 JSON 结构）、说明为什么要把已有记忆的 UUID 重映射成整数。

### 2.2 讲解 + 源码走读

**抽取契约**（`configs/prompts.py:468` `ADDITIVE_EXTRACTION_PROMPT`）：

```json
{
  "memory": [
    {"id": "0", "text": "自包含事实(15-80词)", "attributed_to": "user", "linked_memory_ids": ["1"]}
  ]
}
```

关键约束（`prompts.py:918-943`）：每条事实**自包含**（独立可理解）、15–80 词、可引用已有记忆的 id。`attributed_to` 记录事实归属（user/assistant），`linked_memory_ids` 让 LLM 主动关联相关旧记忆。

**UUID → 整数重映射**（`main.py:924-928`）：

```python
for idx, mem in enumerate(existing_results):
    uuid_mapping[str(idx)] = mem.id
    existing_memories.append({"id": str(idx), "text": mem.payload.get("data", "")})
```

**为什么**：真实 UUID 太长、无规律，LLM 在生成 `linked_memory_ids` 时**容易幻觉出不存在的 id**。重映射成 `"0".."9"` 让 LLM 只面对短整数；返回后再用 `uuid_mapping` 还原真实 id，**幻觉 id 用完即弃，绝不脏写**。这是"给 LLM 一个封闭小词表，防止自由发挥"的工程技巧。

**agent 作用域变体**：当 `filters` 只有 `agent_id` 没有 `user_id` 时（`main.py:931`），系统 prompt 追加 `AGENT_CONTEXT_SUFFIX`（`prompts.py:947`）——以 agent 视角重述事实（"Agent 被告知… / Agent 建议…"），因为 agent 记忆跨用户共享。

### 2.3 小结

- 抽取契约：强制 JSON，每条事实自包含 + 15-80 词 + 可链接旧记忆。
- UUID 重映射成 `"0".."9"` 防 LLM 幻觉 id；幻觉 id 用完即弃。
- agent 作用域追加视角后缀，事实以 agent 视角重述。

### 2.4 课后思考题

- **kp04-02（concept）**：如果直接用真实 UUID 喂给 LLM 做 `linked_memory_ids`，最坏情况下会发生什么？（提示：写脏数据 vs 抽取失败两条路径）

## 3. 为什么 MD5 精确去重而非语义去重（kp04-03）

### 3.1 学习目标

学完你能：说出去重的三层防线、解释为什么不用语义相似度做写路径去重。

### 3.2 讲解 + 源码走读

**三层去重**（从软到硬）：

1. **Prompt 级软去重**：阶段 3 的 prompt 把已有记忆喂给 LLM（`prompts.py:478-549`），LLM 看着旧记忆抽取，天然避免重复——**边际成本为零**（旧记忆本来就要进 prompt）。
2. **MD5 硬去重**：`hashlib.md5(text.encode()).hexdigest()`（`main.py:1010`），对照已存 hash 集合（`main.py:997-1001`）+ 批内 `seen_hashes` set（`main.py:1004,1014`）——**确定性兜底**，文本逐字节相同才跳过。
3. **语义近似留给检索期**：两句"意思相同但文字不同"的记忆不合并，检索期靠融合打分让更相关的排在前面。

**为什么不用语义去重**（这是 design 关键）：

- **阈值不可靠**：多少相似算"重复"？0.9？0.95？不同 embedding 模型对同一阈值语义含义不同（脆弱）。
- **写路径不可逆**：语义去重必然伴随"合并/删除"，一旦合并就不可逆——违背 ADD-only 原则（m06 详述"错误不可在写路径固化"）。
- **成本**：显式 embedding 近邻检查要额外计算；而 prompt 软去重的旧记忆本来就在上下文里。

**证据**：`main.py:1010-1014` 的 MD5 分支明确 `Skipping duplicate memory (hash match)`——精确、零语义判断。

### 3.3 小结

- 三层去重：prompt 软去重（免费）→ MD5 硬去重（确定性）→ 语义近似留给检索期。
- 不用语义去重的三个理由：阈值不可靠、合并不可逆违背 ADD-only、额外成本。
- 去重哲学与 ADD-only 一致：**写路径不做不可逆的裁决**。

### 3.4 课后思考题

- **kp04-03（design）**：如果硬要加语义去重到写路径，你需要额外解决哪两个问题才能不违背 ADD-only？（提示：可逆性 + 阈值稳定性）

## 4. 为什么用实体链接替代图数据库（kp04-04）

### 4.1 学习目标

学完你能：说出实体链接的 5 步流程、解释为什么用轻量 `_entities` 集合替代 Neo4j 图数据库。

### 4.2 讲解 + 源码走读

**实体链接流程**（`main.py:1077-1180`）：

```
① 批量抽实体  extract_entities_batch(文本)      （spaCy）
② 全局去重    归一化实体文本 → 全局实体字典
③ 批量 embed  唯一实体一次 embed_batch
④ 检索匹配    精确(文本) 或 语义(score≥0.95) 匹配已存实体
⑤ 更新/插入  已有实体并集更新 linked_memory_ids；新实体插入 _entities 集合
```

**关键设计点**：

1. **批量优于逐个**：实体批量 embed（`main.py:1098`）、批量 search（`main.py:1128`）、批量 insert（`main.py:1170`）——一次 I/O 处理所有实体，避免 N 次往返。
2. **匹配策略**：精确文本匹配优先（`main.py:1124` `_existing_entities_by_text`），无精确命中再语义匹配（`main.py:1142` `score >= 0.95`）——确定性优先，语义兜底。
3. **关联即加分**：实体 payload 存 `linked_memory_ids`（`main.py:1147-1149`），检索期据此给关联记忆加分（m05 详述）。
4. **失败不致命**：整个实体链接包在 try/except（`main.py:1179`），失败只告警不阻断写入——实体是增强，不是主链路。

**为什么不用图数据库（Neo4j）**（design 关键）：

- **运维成本**：图 DB 部署、备份、扩展成本高，OSS 用户大部分用不上。
- **价值覆盖**：mem0 需要的只是"实体 → 记忆"这层关联，轻量实体向量集合 + `linked_memory_ids` 完全覆盖，无需图遍历。
- **平台保留**：图 memory（多跳关系推理）是 **Platform-only**（OSS 已移除，提交 #6808）——OSS 保持轻，重能力进付费平台。

### 4.3 小结

- 实体链接 5 步：抽实体 → 全局去重 → 批量 embed → 匹配 → 更新/插入。
- 精确匹配优先、语义(≥0.95)兜底；实体关联 = `linked_memory_ids` 加分。
- 实体链接失败只告警不阻断——增强而非主链路。
- 用轻量实体集合替代图 DB：运维成本 + 价值覆盖 + OSS 轻量化。

### 4.4 课后思考题

- **kp04-04（design）**：什么场景下"实体 → 记忆"的轻量关联不够用，必须上真正的图数据库？（提示：多跳关系、反查路径）

## 章节总结

**本章心智模型**：add() 是一条"**蒸馏 + 累积**"管线——8 阶段把对话变成事实，全程只有一次 LLM 调用，且只 ADD 不裁决。三个设计支柱：**防幻觉**（UUID 重映射）、**防重复**（prompt 软去重 + MD5 硬去重）、**增关联**（实体链接）。每个支柱都指向同一个哲学：写路径尽量简单、确定、可逆，复杂度留给读路径。

**关键 file:line 索引**：`main.py:906-1196`（8 阶段）、`:924-928`（UUID 重映射）、`:930-959`（LLM 抽取）、`:997-1014`（MD5 去重）、`:1077-1180`（实体链接）、`prompts.py:468`（抽取 prompt）、`:947`（agent 后缀）。

**与整体架构的钩子**：add() 写的 `linked_memory_ids` 是 m05 search() 实体加分的直接输入；"写路径不裁决"直接预告 m06 的 ADD-only 哲学。
