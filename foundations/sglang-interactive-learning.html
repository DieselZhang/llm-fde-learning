🗺️ SGLang 全景概览

SGLang 是什么？为什么 FDE 需要同时掌握 SGLang 和 vLLM？

🎯 本模块学习目标
  • 一句话说清 SGLang 的定位和核心能力
  • 画出 SGLang 单机/多机/PD 分离三种部署架构的进程拓扑
  • 理解 SGLang 的四大优势场景和六种进程间通信方式

🎯 一句话定位

SGLang 是 LMSYS 组织维护的高性能 LLM 推理框架，核心创新 RadixAttention（前缀树自动缓存复用）。在共享前缀场景（system prompt、few-shot、多轮对话）下性能显著超越 vLLM，每天在 400,000+ GPU 上生成数万亿 tokens。

🔑 FDE 视角
为什么 FDE 必须同时懂 SGLang？ 不同场景选不同引擎--这是 FDE 的核心决策能力。共享前缀多的场景 → SGLang 明显更快；通用场景 → vLLM 更成熟。面试高频：RadixAttention vs PagedAttention、PD 分离部署、sgl-router 原理。

💡 SGLang 四大优势场景

场景技术原因典型收益
共享 System PromptRadix Tree 自动去重相同前缀的 KV CacheTTFT ↓ 50-80%
Few-shot Prompting示例 token 在树中只存一份吞吐 ↑ 2-5x
多轮对话每轮自动复用历史对话的 KV Cache延迟 ↓ 40-60%
结构化 JSON 输出原生 RadixAttention 约束解码代码更简洁

🏗️ 单机部署架构 — 进程全景

SGLang 单机启动时（python -m sglang.launch_server），内部启动以下进程： 

┌──────────────────────────────────────────────────────────┐
│  ① API Server (HTTP + Tokenizer)                         │
│     监听 :30000，接受 OpenAI 兼容请求                     │
│     Tokenization / Detokenization                        │
│     通过 ZMQ 发给 Scheduler                         │
├──────────────────────────────────────────────────────────┤
│  ② Scheduler (主进程)                                    │
│     零开销调度：编译时确定执行计划，运行时几乎不做决策        │
│     管理 Radix Tree（前缀缓存命中/写入/淘汰）               │
│     管理 KV Cache Block Pool（分配/释放）                  │
│     通过 ZMQ 将 batch 分发给 GPU Workers               │
├──────────────────────────────────────────────────────────┤
│  ③ GPU Worker × N (TP=N)                                 │
│     每个 Worker 独占一张 GPU                              │
│     加载模型分片（TP shard）                               │
│     执行 forward pass + RadixAttention Kernel            │
│     Worker 间通过 NCCL 做 AllReduce (TP 通信)         │
├──────────────────────────────────────────────────────────┤
│  ④ (可选) sgl-router — Rust 独立进程                      │
│     追踪所有 Worker 的 Radix Tree 状态                    │
│     将请求路由到缓存命中率最高的 Worker                     │
│     通过 HTTP 与 Worker 通信                           │
└──────────────────────────────────────────────────────────┘

默认端口：API Server 监听 30000，sgl-router 监听 8080（如有）

🔑 关键区分
sgl-router 不是必需的：单 Worker 场景可以直接访问 API Server (:30000)。多 Worker 场景才需要 sgl-router 做缓存感知路由——它知道"哪个 Worker 的 Radix Tree 里已经有这个前缀的缓存"，把请求转发到那个 Worker。

📡 进程间通信方式汇总

通信路径协议/方式传输内容说明

sgl-router → WorkerHTTP转发请求sgl-router 是反向代理
API Server → SchedulerZMQtoken_ids + 元数据进程内通信（同节点）

GPU Worker ↔ GPU WorkerNCCLTP AllReduce 梯度/激活值NVLink/IB，高频低延迟

🔑 FDE 排障要点
四类通信的排障顺序：
① HTTP → curl localhost:30000/health 确认 API Server 活着
② Ray → ray status 确认所有节点在线、GPU 数正确
③ NCCL → NCCL_DEBUG=INFO 看 AllReduce 是否走 NVLink
④ PD 传输 → 检查 NIXL/MoonCake 日志，确认 KV Cache 传输不超时

进程数核对：每个启动的 launch_server = 1 个 Scheduler + TP 个 GPU Worker。所有节点加起来，ray status 显示的 GPU 数应等于各节点 GPU Worker 总和。

🧭 sgl-router、API Server、SGLang Engine 之间的关系

三个概念容易混淆——它们不是替代关系，而是层级叠加。

各自的角色

组件是什么是否独立进程是否必须受众
sgl-routerRust 反向代理，缓存感知负载均衡✅ 独立进程❌ 可选（多 Worker 时推荐）Client → Router
API Server每个 Worker 的 HTTP 入口❌ Engine 进程的一部分✅ 必须Router → Worker / Client → Worker
SGLang Engine整个推理引擎主进程✅ 必须内部组件

无 sgl-router（单 Worker）

Client ──HTTP──▶ API Server (:30000) ──ZMQ──▶ Scheduler ──ZMQ──▶ GPU Workers
                 ↑
                 Tokenization / Detokenization 都在这里
                 API Server = 整个服务的唯一入口

有 sgl-router（多 Worker）

Client ──HTTP──▶ sgl-router (:8080)
                   │
                   │ 查每个 Worker 的 Radix Tree 前缀摘要
                   │ "Worker 1 命中 5 个 token，Worker 2 命中 1 个"
                   │ → 选 Worker 1
                   │
                   └──HTTP──▶ API Server (:30000) ──ZMQ──▶ Scheduler ──▶ GPU
                                ↑
                                API Server 退居"内部接口"
                                不复暴露给客户端

关键澄清

容易混淆的点实际关系
sgl-router 替代了 API Server？不是。sgl-router 是前面的反向代理，每个 Worker 自己的 API Server 照常运行
sgl-router 只是 Nginx？不是。Nginx 不知道"哪个后端有缓存"。sgl-router 追踪每个 Worker 的 Radix Tree 状态
API Server 是独立进程？不是。它是 SGLang Engine 进程的一部分，跟 Scheduler 共享进程空间
sgl-router 和 Scheduler 都做"调度"？不同层面。Router 选 Worker（集群级），Scheduler 管计算（单 Worker 内部）
💡 一句话
sgl-router 决定"给谁算"，API Server 负责"接收请求+Tokenization"，Scheduler 决定"怎么算"。三者各管一层：集群路由 → 请求入口 → 计算规划。
📝 要点回顾
  • SGLang = RadixAttention + 零开销调度 + 原生结构化输出
  • 单机：API Server (ZMQ) → Scheduler (ZMQ) → GPU Workers (NCCL)
  • 多机：sgl-router (HTTP) → Workers × N；跨节点用 Ray + NCCL
  • PD 分离：Prefill → KV Cache (RDMA/NIXL) → Decode
  • sgl-router 可选，多 Worker 时做缓存感知路由

🌳 RadixAttention 深度解析

SGLang 最核心的技术创新--用前缀树（Radix Tree）管理 KV Cache，自动去重。

🎯 本模块学习目标
  • 画出 Radix Tree 结构并解释它如何自动去重前缀
  • 对比 PagedAttention vs RadixAttention
  • 至少举例 3 个典型优势场景

🌲 PagedAttention 的"不够聪明"

请求1: [What][is][the][capital]... → 4 blocks
请求2: [What][is][the][meaning]... → 又 4 blocks
"What is the" 被存了两次 ❌
RadixAttention：所有请求共享一棵树 
        What
         └─ is
             └─ the
                ├─ capital  ← 请求1
                └─ meaning  ← 请求2
"What is the" 只存一次 ✅

📐 Radix Tree 结构示例

              ""
            /    \
   "You are a"   "Explain the"
      /     \           \
"helpful"  "concise"   "concept of"
   /                        \
"assistant"            "RadixAttention"

请求① "You are a helpful assistant"
请求② "You are a concise assistant"（复用 "You are a"）
请求③ "Explain the concept of RadixAttention"（独立路径）

🔀 PagedAttention vs RadixAttention

维度PagedAttention (vLLM)RadixAttention (SGLang)
数据结构Block Table（类似页表）Radix Tree（前缀树）
跨请求共享需配置 enable-prefix-caching默认自动
解决什么问题单序列内显存碎片多序列间缓存冗余
💡 面试金句
"PagedAttention 解决单个序列内部的显存碎片，RadixAttention 解决多个序列之间的缓存冗余。两者不是替代关系--理想情况下，SGLang 内部也用 block 管理，外层用 Radix Tree 做跨请求去重。"
📝 要点回顾
  • RadixAttention = Radix Tree × KV Cache
  • PagedAttention 管单序列内，RadixAttention 管多序列间
  • 共享前缀 → SGLang 明显更快

🔑 关键区分
API Server ≠ sgl-router：API Server 是每个 Worker 自带的 HTTP 入口，负责 Tokenization。sgl-router 是可选的外部反向代理，决定请求发给哪个 Worker 的 API Server。

单 Worker 不需要 sgl-router——客户端直接访问 API Server (:30000)。多 Worker 时，sgl-router 坐在前面，根据各 Worker 的 Radix Tree 缓存状态智能路由。

🔀 Prefill/Decode 分离架构

FDE 进阶技能：计算密集的 Prefill 和内存密集的 Decode 用不同 GPU 集群。

🎯 本模块学习目标
  • 解释 为什么要 PD 分离（资源争抢问题）
  • 理解数据流：Prefill → KV Cache 传输 → Decode
  • 掌握部署命令

🤔 为什么需要 PD 分离？

统一架构问题：同一批 GPU 同时处理 Prefill + Decode
❌ 长 prompt 的 Prefill 抢占 Decode 的计算资源
❌ Decode 的大量 KV Cache 挤压 Prefill 的 batch 空间

PD 分离：
🖥️ Prefill 集群
计算优化 · TP=8 · H100
→ KV Cache →
💾 Decode 集群
内存优化 · TP=8 · H200
✅ Prefill 用 H100（算力强）| Decode 用 H200（显存大）
✅ 高峰期扩 Prefill，长对话扩 Decode（非对称扩缩）

🔧 PD 分离部署

python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-72B-Instruct \
  --disaggregation-mode prefill \
  --tp 8 --port 30001
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-72B-Instruct \
  --disaggregation-mode decode \
  --tp 8 \
  --prefill-url http://<prefill_ip>:30001 \
  --port 30002
📝 要点回顾
  • PD 分离 = Prefill 和 Decode 各自优化、独立扩缩
  • SGLang 用 --disaggregation-mode 一键配置
  • 非对称扩缩是最大优势

⚡ 调度方式对比：Busy Loop vs 零开销调度

两种引擎最根本的架构差异之一：运行时每步决策（vLLM）vs 请求进入时一次规划（SGLang）。

vLLM Busy Loop：每步重新决策

while True:
    ① 扫 waiting queue -- 有新请求吗？
    ② 扫 running queue -- 谁还在跑？
    ③ 算 token 预算 + 数 free blocks
    ④ 调度决策 -- 这轮该算谁？能算多少？
    ⑤ 准备 batch (拼接 input + position_ids + block_diagonal_mask)
    ⑥ forward pass → 采样 → 释放完成的 blocks
    ⑦ 回到 ① -- 下一轮重新决策

每一轮 iteration 都是完整的"决策 → 执行"周期
即使 running queue 连续两轮没变，也要走一遍决策逻辑
高并发时 CPU 调度开销不可忽略

SGLang 零开销调度：请求进入时一次规划

请求进入 SGLang:
  ① Radix Tree 查找 → "哪些 token 已有缓存？从哪开始是新 token？"
  ② 精确知道：需要多少新 KV blocks、需要多久 Prefill

  → 编译时生成执行计划（一次完成，不再改变）:
     Step 1: 分配 blocks → Prefill 新 token
     Step 2-N: Decode (每步 1 token)

运行时:
  每步直接按计划执行 → 不需要重新决策
  CPU 开销几乎为零（只发指令不决策）

核心差异

维度vLLM Busy LoopSGLang 零开销
决策时机每步 iteration 动态决策请求进入时一次规划
决策依据free blocks + token 预算 + 优先级Radix Tree 缓存命中 + 预编译计划
CPU 开销每步 ~0.1-0.5ms每步 ~0.01ms
灵活性高（可随时调整优先级、抢占）较低（计划固定）
前提条件无特殊要求依赖 Radix Tree 提供精确前缀命中信息
🔑 根本原因
vLLM 的哈希表只能回答"某个 16-token block 在不在"（碎片化信息），无法告诉你"前 200 个 token 全命中，从第 201 个开始是新内容"。SGLang 的Radix Tree沿着树走一次就知道完整的命中和分叉点（连续信息）。信息粒度不同 → 决策方式不同。
📝 要点回顾
  • SGLang 胜在共享前缀场景
  • vLLM 胜在通用场景和成熟度
  • vLLM: 运行时每步决策（灵活，CPU 有开销）
  • SGLang: 编译时一次规划（零开销，依赖 Radix Tree）
  • 最佳实践 = 两个都部署，按场景路由
