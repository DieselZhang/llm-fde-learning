🔑 关键结论： vLLM 是一个推理引擎。它不训练模型，只负责高效地"使用"已经训练好的模型。推理的核心挑战是在有限显存下最大化吞吐、最小化延迟。

LLM 生成文本是一步一步的，每次只生成一个 token（一个词或子词），然后把新 token 追加到输入后面，再生成下一个：

输入: "今天天气" → 模型 → "真"
输入: "今天天气真" → 模型 → "好"
输入: "今天天气真好" → 模型 → "！"

🔑 注意：每次生成新 token 时，模型要重新"看"一遍所有之前的 tokens。如果每次都从头计算 Attention，计算量会以 O(n²) 增长。这就是 KV Cache 要解决的问题。

没有 KV Cache 的世界：

生成第 1 个 token：计算 Attention("今天","天气","真","好") → 生成 "！"
生成第 2 个 token：计算 Attention("今天","天气","真","好","！") → 重新算了前 4 个！
生成第 500 个 token：计算 Attention(前面 504 个 tokens) → 每次都重算，O(n²) 爆炸

有 KV Cache 的世界：

生成第 1 个 token：计算 Attention(全部) → 把 K,V 存起来 → 生成 "！"
生成第 2 个 token：只需要算新 token "！" 的 Attention →复用之前存好的 K,V → O(n) 而非 O(n²)
生成第 500 个 token：只需算 1 个新 token → 计算量恒定！

🔑 KV Cache 就是把之前算过的 Attention 中间结果（Key 和 Value）缓存起来，避免重复计算。代价是需要大量显存来存储——这就是 PagedAttention 要解决的显存管理问题。

维度Prefill（预填充）Decode（解码）
做什么一次处理整个 prompt的所有 token逐 token 生成输出
计算特征计算密集型（大量矩阵乘法）内存密集型（大量读取 KV Cache）
GPU 利用率高（矩阵满载）低（大部分时间在等显存读取）
每次处理的 token 数N 个（prompt 的全部 token）1 个（每次只生成 1 个）
影响指标TTFT（首 token 延迟）TPOT（每 token 生成时间）
💡 理解这个很重要
Prefill 和 Decode 的资源需求是相反的：Prefill 需要大量计算但不需要太多显存带宽，Decode 几乎不计算但严重依赖显存带宽。这就是为什么会有 PD 分离架构（把 Prefill 和 Decode 放到不同的 GPU 节点上）。

GPU 显存（HBM，如 H100 的 80GB HBM3）的容量远小于 CPU 内存（通常 512GB-2TB），但带宽极高（H100: 3.35TB/s）。推理的瓶颈往往是显存容量而非算力。

存储层级典型容量带宽存什么
GPU HBM（显存）80GB (H100)~3.35 TB/s模型权重 + KV Cache
CPU DRAM（内存）512GB-2TB~100 GB/s操作系统 + 缓冲数据
NVMe SSD2TB-8TB~7 GB/s模型文件（加载前）

🔑 一个 70B 参数的模型（FP16）本身就占 ~140GB 显存，两张 H100 才放得下。KV Cache 还要额外占用——这就是 vLLM 试图高效管理的珍贵资源。

🤔LLM 推理有多难？

假设你要上线一个 Llama-3-70B 的聊天服务，支持 100 人同时使用。直观挑战：

  • 模型本身占 ~140GB 显存（FP16），两张 H100 才放得下

传统的做法（用 HuggingFace Transformers 直接跑）吞吐量极低，显存浪费严重——这就是 vLLM 要解决的问题。

🔀Engine Core 内部调度循环

# Engine Core 的 busy loop（核心调度逻辑）
while True:
    new_requests = receive_from_api_server()        # 1. 接收新请求
    scheduled = scheduler.schedule(                  # 2. 调度决策
        waiting_queue + running_queue,
        available_kv_blocks                          # KV Cache 剩余容量
    )
    for req in scheduled:
        kv_cache_manager.allocate(req)               # 3. 分配 KV blocks
    outputs = dispatch_to_workers(scheduled)         # 4. 分发 GPU Workers
    for output in outputs:                           # 5. 处理输出
        if output.finished:
            kv_cache_manager.free(output.request)    # 释放 KV blocks
        send_to_api_server(output)

🔍 TTFT 排查决策树

TTFT 偏高？
├─ 排队时间长？ → num_requests_waiting 高
│ → 增大 --max-num-seqs 或降低 --max-model-len
├─ Prefill 时间长？ → check vllm_prefill_duration
│ ├─ Prompt > 4K tokens → 开启 --enable-chunked-prefill
│ ├─ 公共前缀 → 开启 --enable-prefix-caching
│ └─ GPU 利用率低 → nvidia-smi 检查是否有进程抢占
└─ Tokenization 慢？ → 极少见，检查多模态编码
🔑 TTFT 三步法
① 定位阶段（Prometheus 指标区分排队 vs 计算）→ ② 看资源（nvidia-smi + vllm_num_blocks_available）→ ③ 调参数

⚡FlashAttention -- 推理加速的"隐藏基石"

模型初始化阶段最容易报错的组件。它不改变模型结构，但没有它，Prefill 速度会慢 2-4 倍。

核心问题：Attention 的中间矩阵太大

标准 Attention:
  Q x K^T → attention_scores [4096, 4096] ≈ 32 MB  ← 必须写回显存再读出来
  Softmax → attention_weights [4096, 4096] ≈ 32 MB
  x V → 输出

FlashAttention:
  Q,K,V 分块加载到 GPU 片上 SRAM（比 HBM 快 10 倍）
  → 在 SRAM 里算完局部 Attention → 直接累加 → 中间矩阵从不写回显存
  → 显存 IO 减少 ~30%，实际速度提升 2-4x

跟 TP/PP/DP 的关系

关系说明
直接关系几乎没有。FlashAttention 是 Attention Kernel 实现优化（怎么算），TP/PP/DP 是分布式策略（在哪算、谁算哪部分）
在 TP 中每个 GPU 独立执行 FlashAttention（算各自分到的 head），不参与跨 GPU 的 AllReduce 通信
间接收益FlashAttention 省下的临时显存（~2.5GB for 70B）让同样 TP 下能分配更多 KV Cache blocks
在 PP/DP 中无特殊关系--每个 GPU 各自受益于 FlashAttention 的加速

为什么启动时容易报错

FlashAttention 包含编译好的 CUDA kernel，安装时需要在本地编译：

常见失败原因排查
CUDA toolkit 版本不匹配nvcc --version vs nvidia-smi 对比
GPU 架构不支持（老卡 SM < 80）A100/H100 正常；V100 需旧版 flash-attn
nvcc 未安装或不在 PATHwhich nvcc
编译超时/内存不足MAX_JOBS=1 pip install flash-attn 限制并行编译
⚠️ 如果没装
vLLM 自动回退到 xformers 或 PyTorch native attention。能跑，但Prefill 慢 2-5 倍 + OOM 风险更高。生产环境必须安装。

📝 要点回顾
  • vLLM V1 是多进程架构：API Server (HTTP+Tokenization) → Engine Core (调度+KV) → GPU Workers (计算)
  • Engine Core 是单进程 busy loop，调度和 KV Cache 管理在同一个进程中零延迟协同
  • 模型加载最危险是阶段 3（KV Cache 预分配）——OOM 高发地
  • TTFT 70-90% 花在 Prefill 上，排查从区分"排队"还是"计算"开始

📄 PagedAttention 深度解析

vLLM 最核心的技术创新。借鉴操作系统虚拟内存的分页思想，解决 KV Cache 显存碎片问题。

🎯 本模块学习目标

🧠KV Cache 显存占用有多严重？

70B 参数模型（Llama-3-70B），seq_len=4096：

  • 单个请求 KV Cache ≈ 3.2 GB
  • 1024 并发 ≈ 3.2 TB 😱
  • 传统连续分配：利用率仅 20-40%

公式：M = 2 × layers × kv_heads × d_head × seq_len × 2(K+V) × bytes_per_element

🔧Continuous Batching 底层如何实现？

核心挑战：三个请求处于三个不同阶段（一个 Prefill、两个 Decode），如何让它们在一次 GPU forward pass 中同时计算？

机制一：超序列拼接

把所有请求的 token 拼成一个一维数组，GPU 一次 forward pass 全部处理：

请求A (Decode, 历史 5 tokens): 需要算 [A_5]
请求B (Prefill, prompt 4 tokens): 需要算 [B_0, B_1, B_2, B_3]
请求C (Decode, 历史 3 tokens): 需要算 [C_3]

input_ids = [A_5, B_0, B_1, B_2, B_3, C_3]
不需要 GPU 知道"这是 3 个请求"——它只看到一个 [6, hidden_dim] 的输入

机制二：Position IDs — 告诉模型真实位置

拼接后 token 在数组中的位置 ≠ 它在原始序列中的真实位置。需要通过 position_ids 告诉 RoPE 每个 token 的真实位置：

input_ids 数组: [A_5, B_0, B_1, B_2, B_3, C_3]
在 batch 中的索引: 0 1 2 3 4 5
position_ids = [5, 0, 1, 2, 3, 3]
A_5 是请求A 的第 5 个 token（前面有 5 个历史）；C_3 是请求C 的第 3 个

机制三：Block Diagonal Attention Mask — 阻止跨请求"偷看"

最关键的机制：拼接在一起的 token 绝对不能互相看到。每次 forward pass 动态构造块对角 mask：

Attention 矩阵 (谁可以看到谁):
            A_5  B_0  B_1  B_2  B_3  C_3
      A_5 [  1    0    0    0    0    0  ]  ← A_5 只看自己和历史(不在本次 input 中)
      B_0 [  0    1    0    0    0    0  ]  ← B_0 是第一个 token，只看自己
      B_1 [  0    1    1    0    0    0  ]  ← B_1 能看到 B_0 和自己
      B_2 [  0    1    1    1    0    0  ]
      B_3 [  0    1    1    1    1    0  ]
      C_3 [  0    0    0    0    0    1  ]  ← C_3 只看自己(历史在 KV Cache 里)

同请求的 token 可以互相看到 (块内连接)；跨请求的 Attention 被 block 为 0 ✅

机制四：Block Table — 历史 KV Cache 的非连续访问

不仅 input 是拼接的，历史 KV Cache 的访问也依赖 PagedAttention 的 block table：

请求A 的 block_table: [42, 137] ← 2 个物理 block 存着 tokens 0~15 的 K,V
请求B 的 block_table: [7, 8] ← Prefill 刚写入的
请求C 的 block_table: [99] ← 1 个物理 block

Attention Kernel 根据各自的 block_table 加载对应物理 block 的 K,V
→ 物理上不连续，但逻辑上每个请求看到的是"完整连续的 KV Cache"

机制五：一次完整 Step 的调度执行

Scheduler Step:
① 检查 waiting queue → 请求B 进来 → 分配 KV blocks → waiting→running
② 检查 running queue → 请求A 继续、请求C 继续
③ 准备数据 → input_ids + position_ids + attn_mask + block_tables
④ 一次 Forward Pass → 6 个 token 同时计算
⑤ 采样 → A 生成 "呀"、B 生成首 token "春"、C 生成 EOS → 完成
⑥ 后处理 → C 释放 blocks → A,B 继续在 running → 下轮迭代

为什么 Prefill 和 Decode 能混在一起？

在 Attention 层面，Prefill 的 token 和 Decode 的 token 只是"长度不同"，都是普通的矩阵运算。请求B 的 4 个 token 互做 Self-Attention（正常 Prefill），请求A 的单 token 与历史 KV Cache 做 Attention（正常 Decode）。Block Diagonal Mask 确保它们互不干扰——混合 batch 的额外开销（构造 mask + 拼接 input）相比较 forward pass 的计算时间几乎可忽略。

Chunked Prefill 如何融入

长 prompt（如 20000 tokens）不能一次性 Prefill。它被拆成多个 chunk，每批大小由 max-num-batched-tokens 控制，chunk 之间穿插普通 Decode：

Step M: Prefill chunk tokens[0:4095] → 写 KV blocks → 请求回到 waiting 继续排队
Step M+1: Decode batch (其他短请求) → 穿插！
Step M+2: Prefill chunk tokens[4096:8191] → 追加 KV blocks → 继续排队
Step M+3: Decode batch → 穿插！
...直到全部 prompt 处理完 → 进入 running queue → 开始 Decode
✅ 长 prompt 不阻塞短请求 —— 这是 Chunked Prefill 的核心价值
🔑 FDE 视角
Continuous Batching = 五个机制协同：超序列拼接 + Position IDs + Block Diagonal Mask + Block Table + Iteration-level 调度。这五个机制让 Prefill(计算密集) 和 Decode(内存密集) 的 token 可以在一次 GPU forward pass 中同时处理——这是 10-20x 吞吐提升的根本原因，不是简单的"动态 batch"。

⏱️Chunked Prefill — 进一步优化

传统 Prefill 一次性处理整个 prompt，耗时较长，阻塞其他请求。Chunked Prefill 将 prompt 拆分为多个 chunk：

传统： [===== 整个 Prompt =====] → 阻塞 → Decode
Chunked： [Chunk1] → [Chunk2] → [Chunk3] → Decode
✅ chunk 之间可穿插其他请求的 decode

🔀三种并行策略对比

策略原理通信量适用场景vLLM 配置
TP每层权重矩阵切分到多 GPU🔴 高（每层 AllReduce）单机多卡--tensor-parallel-size N

经验法则：DP > TP > PP（通信开销从小到大）

🔧PD 分离（Prefill-Decode Disaggregation）

将 Prefill（计算密集型）和 Decode（内存密集型）分配到不同的 GPU 集群，各自用最优硬件、独立扩缩容。

为什么需要 PD 分离？

统一架构的问题：同一批 GPU 同时跑 Prefill + Decode
❌ 长 prompt 的 Prefill（算力全满）抢占 Decode 的计算资源
❌ 高并发 Decode（KV Cache 吃满显存）挤压 Prefill 的 batch 空间
❌ 无法为两种完全不同的负载选择最优硬件

PD 分离：
🖥️ Prefill 集群
计算优化 · H100 · TP=8 · Batch=64
→ KV Cache 传输 →
💾 Decode 集群
内存优化 · H200 · TP=4 · Batch=256
✅ Prefill 用 H100（算力强、成本低），Decode 用 H200（显存大、141GB）
✅ 独立扩缩：高峰期扩 Prefill，长对话扩 Decode（非对称扩缩）

完整数据流

Step 1: Prefill 节点处理
  接收 prompt → 一次性计算全部 KV Cache → 采样生成首 token

Step 2: KV Cache 传输
  Prefill 节点将 全部 KV Cache blocks + 首 token + 请求元数据 传给 Decode 节点
  传输通道：NIXL / MoonCake / RDMA（GPU 显存到 GPU 显存直通，不走 CPU 内存）
  短 prompt (~128 tokens)：~40 MB → ~3ms | 长 prompt (~4096)：~1.25 GB → ~100ms

Step 3: Decode 节点继续
  接收 KV Cache → 写入本地 GPU 显存 → 逐 token Decode 直到 EOS
  每步只需读 KV Cache（内存）+ 算 1 个新 token 的 Attention

Step 4: Prefill 侧 blocks 处理
  传输完成后：倾向保留为缓存（Prefill 节点显存压力不大）
  → 下一个相同前缀的请求命中 → 不用重算 + 不用再传

vLLM PD 分离部署 — 与 SGLang 的关键差异

⚠️ 重要区分

📡PD 分离中的 KV Cache 传输 -- 怎么传、怎么看日志、怎么配通

传输通道：GPU 显存到 GPU 显存直通

不是 HTTP、不是 ZMQ、不是 TCP。KV Cache 通过 GPUDirect RDMA 直接从 Prefill GPU 显存经网卡推到 Decode GPU 显存，全程不经过 CPU 内存。vLLM 用 NIXL（NVIDIA 官方）或 MoonCake（字节开源）插件管理传输。 

Prefill GPU 显存 ──GPUDirect RDMA──▶ IB 网卡 ──400Gbps──▶ 对端 IB 网卡 ──▶ Decode GPU 显存
     ↑                                                                    ↑
  不经过 CPU 内存                                                    不经过 CPU 内存

两个集群怎么配通？

🔗 vLLM 如何发现 Ray 集群？

vLLM 不需要在命令行参数中指定 Ray 地址。它通过 环境感知 自动判断：

vllm serve ... 启动时内部逻辑:

if 检测到 RAY_ADDRESS 环境变量 or 本地已有 Ray 进程:
  → 调用 ray.init(address="auto") 自动连接集群
  → GPU Workers 通过 Ray Actor 跨节点分布
else:
  → 使用本地 Python multiprocessing
  → GPU Workers 作为本地子进程启动

关键：ray start --head 会自动设置 RAY_ADDRESS 环境变量。你在同一台机器上启动 vLLM 时，它自动就能连上。

⚙️ Ray 在 vLLM 中的作用：分布式进程管理器

vLLM 启动时，根据 TP × PP × DP 计算出需要的 GPU Worker 数量（如 TP=8, PP=2 → 16 个 Worker）。然后通过 Ray 在集群中创建 Ray Actor：

没有 Ray (单机):
  vLLM → Python multiprocessing → N 个本地子进程，每个绑一张 GPU

有 Ray (多机):
  vLLM → ray.init(address="auto") → 创建 Ray Actors
  每个 Actor 用 @ray.remote(num_gpus=1) 声明需要 1 张 GPU
  Ray 自动决定 rank=0~7 放机器A，rank=8~15 放机器B
  → 你不需要手动指定每个 Worker 的位置！

⚠️ 常见踩坑与排查

现象原因排查/解决
Worker 节点不显示 GPU 每台 Worker 忘了执行 ray start ray status 看 Node count 和 GPU 总数；在 Worker 上执行 ray start --address=...
vLLM 只用头节点的 GPU Worker 节点 Ray 未连接或 GPU 不可见 每个节点单独验证 nvidia-smi；确保加入集群前 GPU 驱动正常
Ray 版本不一致报错 不同节点 pip 安装的 Ray 版本不同 pip install ray==2.9.0 统一版本；所有节点一致
头节点重启后 Worker 掉线 ray stop 不会通知 Worker 重连 每个 Worker 重新执行 ray stop && ray start --address=...
NCCL 跨节点通信超时 NCCL 用了错误网卡或防火墙阻挡 NCCL_DEBUG=INFO 看日志；export NCCL_SOCKET_IFNAME=ib0 指定高速网卡
多机下 CUDA 版本不一致 不同节点装的 CUDA toolkit 版本不同 nvcc --version + nvidia-smi 对比；统一镜像部署
🔑 FDE 视角
vLLM + Ray 的核心关系：vLLM 不传 Ray 地址 → 通过 ray.init(address="auto") 自动检测环境变量 → Ray 作为分布式进程管理器分配 Worker 到各节点 → vLLM 只关心"我有 16 个 Worker"，不关心"它们在哪个物理节点"。

排查口诀：ray status 看集群 → 每节点 nvidia-smi 看 GPU → NCCL_DEBUG=INFO 看通信 → vLLM 日志看 Worker 数是否匹配 TP×PP×DP。
📝 要点回顾
  • vllm serve 模型路径 是最小启动，其余参数根据场景叠加
  • 每个参数都在控制显存分配：utilization、max-model-len、TP size
  • 多机部署的核心：ray start --head 在各 Worker 节点 ray start --address=...，vLLM 通过 ray.init(address="auto") 自动发现集群，不需要传 Ray 地址
  • Ray 在 vLLM 中扮演 分布式进程管理器：用 Ray Actor 自动将 GPU Worker 分配到各节点
  • 排查四件套：ray status → nvidia-smi → NCCL_DEBUG=INFO → vLLM 启动日志

🎛️ 性能调优

FDE 核心竞争力：知道每个参数调了会影响什么。

🎯 本模块学习目标
  • 区分 8 个关键参数的影响级别（🔴关键 / 🟡中等 / 🟢高级）
  • 掌握 FDE 调优三原则：先量后调、一参一变、显存第一
  • 知道 nvidia-smi 和 dcgmi dmon 是最常用的监控工具
--gpu-memory-utilization关键

GPU 显存使用比例（默认 0.90）。过高→OOM；过低→浪费。从 0.85 开始上调。

--max-model-len关键

最大上下文长度。不要设得比实际需求大太多，否则 KV Cache 吃满显存。

--max-num-seqs关键

最大并发序列数。越大并发越高但每请求 KV Cache 越少。权衡并发 vs 延迟。

--tensor-parallel-size中等

TP 切分数（2 的幂）。越大单请求延迟越低，通信开销也越大。

--block-size高级

KV block 大小（默认 16 tokens）。越大越快但可能浪费内存。

--max-num-batched-tokens中等

单次迭代最大 token 数。影响 GPU 利用率，越大效率越高延迟也越高。

--enable-prefix-caching关键

前缀缓存。有共享 system prompt 时强烈建议开启。

--enable-chunked-prefill中等

分块预填充。长 prompt 下建议开启，避免 Prefill 阻塞 Decode。

🔑 调优三原则
① 先量后调：benchmark 先测现状 ② 一参一变：每次只改一个参数 ③ 显存第一：nvidia-smi 和 dcgmi dmon 是 FDE 最好的朋友
📝 要点回顾
  • 显存相关参数（utilization、max-model-len、max-num-seqs）影响最大
  • --enable-prefix-caching 和 --enable-chunked-prefill 是性价比最高的两个开关
  • 调优前先 benchmark，每次只改一个参数，永远先看 nvidia-smi
